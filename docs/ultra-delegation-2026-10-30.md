# Ultra 主动委派校准（2026-10-30）

## 发现

排查确认 Ultra 可正常保存并进入模型请求，`agent_tool` 也属于默认可见工具；不是简单的菜单未生效或默认容量不足。

实际策略只要求模型“检查”独立调查/验证机会，没有明确鼓励执行委派。同时工具描述将子任务限定为复杂多步工作，且工具说明错误地建议“最终回答需要结果时，使用 run_in_background=false”。实际上需要结果与提前阻塞是两回事；独立任务可以先后台启动，主代理继续推进，汇总前再等待。

这些指令会抬高委派门槛，但仅凭源码不能证明它们是模型不派发的全部原因。

## Codex 对照

本地固定提交 [`c9750d7`](https://github.com/openai/codex/tree/c9750d7f50052b29f53def02b5cf2160ae49a3d9) 的 [`multi_agent_mode_instructions.rs`](https://github.com/openai/codex/blob/c9750d7f50052b29f53def02b5cf2160ae49a3d9/codex-rs/core/src/context/multi_agent_mode_instructions.rs) 将明确请求模式和主动模式作为不同的 developer 指令片段。具体启用还经过 [`session/multi_agents.rs`](https://github.com/openai/codex/blob/c9750d7f50052b29f53def02b5cf2160ae49a3d9/codex-rs/core/src/session/multi_agents.rs) 的配置与模型消息解析，不能说只有一个固定提示词。

官方 [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) 区分本地 Codex 的显式/项目指令委派和 ChatGPT Work Ultra 的主动委派；[Responses Multi-agent](https://developers.openai.com/api/docs/guides/responses-multi-agent) 也说明可通过 developer 指令调整主动委派策略。不能把这些入口的默认行为混为“所有 Codex 都会自动拆任务”。

Xuloom 继续让协作档位独立于模型思考强度，不复制 Codex 中 Ultra 思考强度到协作模式的绑定。

## 修改

- Ultra：有收益的独立研究、不同方案、验证任务应主动尽早派发；主代理保留关键主线和最终综合。简单或严格串行任务直接处理。
- Auto 保留选择性委派，Solo 继续禁止委派。权限、思考强度、宿主容量、累计额度和递归规则不变。
- 工具描述改为可交给 worker 的有边界的独立任务，不再要求每个子任务本身都是复杂多步任务。
- 独立任务优先后台发起，只有确实无其他工作可推进时才前台等待；最终仍复用现有结果等待和完成保护。
- 没有增加隐藏规划调用、自动起代理、固定数量或“未派发就反复请求模型”的机制。原程序调用的 `run_in_background` 默认值仍是 false，未改变既有 API 的阻塞/返回语义。
- 修改现有策略和工具说明，没有增加全局提示段。Ultra 策略文本由 1127 减至 1079 字符；数字限额继续由原 Runtime 执行，可查询实际 capacity。

## beta.21：用户复测后仍未自主委派

更新 beta.20 后的 Ultra 会话仍连续使用搜索、网页和文件工具，没有提交 `agent_tool` 请求，工作区也未加载会覆盖策略的指令文件。因此没有证据把这次问题归因于权限拦截、容量限制或旧 EXE。beta.20 的载荷测试只能证明规则传入模型，不能证明该模型会主动派发；先前修改未完成行为层面的验收。

本次将协作策略从冗长的工具规则中移出，使用单独的会话段落，放在工具说明之后。压缩请求与正常运行使用相同入口；每次请求只包含一份当前协作策略。Ultra 明确将用户选择该档位解释为主动协作要求：实质任务有独立分支时，应早期委派，而不是自己逐一包办所有分支。简单问答及严格串行任务仍直接处理。Auto/Solo、权限、数量限制及递归约束不变。

没有强制 `tool_choice`、关键词分类器、隐藏规划模型调用或无意义 worker。这个改动改善策略的可见性和明确程度，仍不是模型遵从率保证。是否真的改善目标模型的自主委派，需要另行获得远端验收授权，不能拿本地替身测试代替。

新增本地链路回归覆盖：通过父代理真实模型流入口提交原生后台派发；两个 worker 等待期间，父代理仍执行自己的工具；父代理提前给出最终回答时，原完成保护等待全部 worker 并用其结果重新汇总。该测试验证执行链路，不测试真实模型自主选择。

本地 Python 3.12 全量最终运行 347 项，346 通过、1 跳过（`desktop/build/ultra-policy-final-regression.log`）。协作专项 15 项、暂存资源中的包内 Python 15 项、TypeScript/Vite 构建及源码桌面协作端到端通过。原安装资源已更新为 beta.21 / 构建 `20261030-161322`，保留原 EXE 和回滚资源，未结束用户应用。

更新后的原 EXE 隐藏窗口协作端到端、安装资源中的包内 Python 15 项也通过；使用隔离测试配置和本地协议服务，没有向用户远端模型提交验收请求。未发布新的 Release。

## beta.26：角色参数与前台默认（2026-10-31）

本次实际会话出现了两次 `agent_tool` 调用：第一次选择未注册的 `research` 类型而失败，第二次改用 `general-purpose`，成功创建一个 worker。第二次没有传 `run_in_background`，旧默认是前台等待，主代理因此停在当前工具调用中。不能把这条记录解释成“完全没有调用子代理”，也不能把仅启动一个文献分支视为已经满足多方向主动协作预期。

- 两个派发入口的角色参数按当前有效注册角色生成枚举，包含内置、用户角色和有效 Skill 附带的角色。省略仍使用 `general-purpose`；不会把未知名字静默映射成另一个权限角色。
- 输入的语义校验移到审批和执行之前。未知角色返回 `invalid_tool_input / executed=False` 与有效角色列表，使用现有参数修复流程；不再误报执行效果不确定，也不创建 worker。
- 模型调用 `agent_tool` 时省略后台参数默认 `true`，和 `spawn_agent` 一致。显式 `false` 仍等待；版本化 `engine.agents(...)` 和直接 `.execute(...)` 保留原有前台默认。最终结果等待、取消、权限、Solo、数量限制均复用原实现。
- 过程行明确显示“启动子代理 / 等待子代理”，减少“管理子代理”这一含混描述。

没有继续扩充 Ultra 全局提示、增加隐藏规划请求、强制工具选择、固定代理配额或第二套调度器。这次修复减少已观察到的机械失败和父代理阻塞；不能据此保证目标模型自主委派的频率。

协作专项 20 项、暂存资源中的协作与程序接口 24 项、桌面逻辑 51 项、构建、源码桌面协作与 40 个子代理端到端均通过。端到端首次新增枚举断言遗漏了内置 Skill 提供的 `software-engineer` 有效角色，已修正断言并重跑通过。所有测试使用隔离配置和本地确定性接口，未调用用户远端模型；私人 Skill 与聊天正文未写入源码或发行资源。
