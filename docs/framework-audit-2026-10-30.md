# 框架排查与修复记录（2026-10-30）

## 范围与方法

基于 beta.16，先运行原有全量测试，再检查全部 Python 模块的语法与未定义变量；人工重点审查文件工具、写入后观察器、原生命令与后台任务、工具回执和进程清理。权限、会话单写者、子代理、预算、MCP、持久化和恢复同时通过现有契约测试回归。这不等于逐条证明所有生产场景可靠。

没有调用用户的远端模型，没有修改私人 Skill、接口配置、用户会话或任务文件。桌面测试使用隔离配置、隐藏窗口和本地协议服务。

## 已确认并修复

| 问题 | 修复与证据 |
| --- | --- |
| 修改记录器调用 `os.path` 却没有导入 `os` | 补齐导入；使用真实缓存、产物记录器、写队列和修改记录器验证写入、编辑与 Notebook 路径 |
| 文件写完后，辅助记录异常导致工具错误，诱发重复覆盖 | 写后缓存、产物和可选验证记录共用受保护的观察入口；返回 `write_applied=true`、具体警告和不要重放的说明。文件写入本身失败仍失败；会话持久化失败仍按原协议暴露 |
| Shell 名称和说明暗示 Bash，但 Windows 实际使用 cmd | 保留兼容工具名，明确实际 Shell、语法限制，推荐结构化 `argv/stdin`；使用会话工作目录并遵循工作区路由 |
| Windows 本地编码被固定当作 UTF-8 | 优先严格 UTF-8，失败后按 Windows 控制台/OEM/ANSI 编码解码；用于前台、后台、Hook 和分页命令输出；原始命令日志仍保存字节 |
| 旧 Shell 工具自行截掉 30,000 字符后的输出 | 移除这层不可恢复截断，复用公共完整结果归档和读取入口；验证尾部标记仍在完整文件里 |
| 旧 Shell、Git 探测、后台任务及 Hook 的停止只杀父进程或未正确等待 | 使用同一套自有进程启动与进程树清理；超时及取消等待清理。后台启动失败会关闭已打开的日志句柄 |
| 分页命令的输出上限或磁盘失败可能留下管道等待/错误状态 | 停止进程时继续排空管道，输出失败返回 `storage_error`，不伪装完成；故障注入检查百万字节输出与日志打开失败 |
| 命令初始回执写盘失败可能留着已经启动的进程；最终回执失败仍显示完成 | 初始保存失败清理已启动进程；最终保存失败明确存储错误；通知回调异常不改变真实执行结果 |
| 命令 JSON 内部状态失败，但工具卡片可能显示成功 | 引擎识别原生命令的失败、取消、超时、输出上限、存储失败状态；通过真实引擎回执测试 |
| Notebook 的部分错误字符串没有匹配通用失败前缀 | Notebook 错误统一为明确的结构化错误结果，验证写入拒绝不会显示成功 |
| 工作区路由提示可能前置到命令 JSON，破坏程序读取 | 原生命令控制 JSON 不添加文字前缀；回执中的实际 `cwd` 保留路由证据 |
| 执行后的通用异常缺少副作用提示 | 回执包含 `handler_invoked` 与 `effects`，已开始执行时明确要求检查现状，不能盲目重放 |

## Pi 参考与边界

核对了 Pi 当前源码中的 [写文件](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/tools/write.ts) 和 [Shell](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/tools/bash.ts)：其写入工具采用父目录递归创建和文件变更队列；Shell 明确选择执行后端，支持进程树清理及完整输出读取。这些实现可参考，但没有证据证明 Pi 不存在 Bug，也不能把我们的测试通过说成“框架所有 Bug 均已排除”。

编码推断不能保证识别任意二进制/混合编码；原始日志仍是复核依据。进程清理针对本次任务拥有的进程；不能等同于操作系统沙箱，主动脱离父进程的程序仍需要单独的系统隔离和验证。跨进程竞争、机器崩溃、任意时刻的文件部分写入及远端故障仍有更广的状态空间。
